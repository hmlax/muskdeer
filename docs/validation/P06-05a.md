# P06.5a 最终额度检查的锁顺序

日期：2026-10-27。关联 R03/R05、A07/A09/A12 的并发回归。

审查发现版本15的global门禁按意图→全局额度读取，后续门禁才取得账户预算；另一意图确认释放按账户预算→全局额度修改，存在循环等待。受控真实PG用例在两个自有backend都达到实际Lock等待后释放提交检查点，修正前明确报deadlock detected：释放方等待risk_budgets，提交方等待account_budgets。

迁移16替换最终global门禁，先取得账户/策略预算，再读取意图/全局额度，保持金额和身份断言，保留已提交迁移15。测试额外检查点仅在独立测试schema中以校验和DDL安装，不进入生产迁移；使用生成Model和pg_stat_activity观察本测试捕获的backend，不靠随机sleep控制交错。所有goroutine/SQL事务有原生期限和取消/join。

同一用例先红后绿，相关race通过（0.70秒）。最初夹具的PID查询继承作用域/扫描不匹配已修正，保存真实deadlock红例 .cache/p06-05a-deadlock-red.log；绿例 .cache/p06-05a-green.log。完整make verify、完整make integration、文档/差异检查通过，lint 0 issues；基础设施24.853秒、业务40.673秒，受控回归在全套中0.36秒通过，race/goleak与隔离清理保留。

依据：PostgreSQL 16的[触发器执行顺序](https://www.postgresql.org/docs/16/sql-createtrigger.html)及[行锁/死锁说明](https://www.postgresql.org/docs/16/explicit-locking.html)。测试使用真实数据库行为验证该交错，文档本身不代替回归。
