# P16.2D — 撮合目标拥有失联撤单与恢复保护

2026-11-03；基线 `01d2d73`，分支 `codex/two-apps`。

失联撤单由 matching-engine 自有生命周期执行，独立于订单网关/Go 进程。已挂订单绑定原 producer 双 proof；目标每 200ms 检查当前租约，不延长租约，不将下单队列期限误当成挂单期限。失效后调用原生撤单链路，仅撤剩余量，保留实际成交证据；扫描按 128 项有界分页，接管资金账户最多 64 张有效订单（本轮 20 档双边为 40 张）。

正常停止在普通队列排空后，撤完接管报价并等待任务结束，再清理发布器；取消所有者异常时关闭撮合进程，避免继续接受风险。新风险的最终执行检查拒绝没有取消所有者的状态。恢复时不恢复旧进程租约，在独占恢复屏障内撤销失去所有权的接管挂单，然后才打开普通交易；其他资金账户保持。

实际完整原生 `cargo test --locked --workspace --all-features --no-fail-fast` 退出 0：1699 passed、0 failed、38 原有 ignored。四项新增测试验证部分成交后只撤剩余报价、恢复先撤再开放且保留其他账户、拥有者停止时撤活跃报价并清理 readiness、取消所有者不就绪及 64 张上限。两个原生项目格式检查通过；本轮新增 Clippy 分支样式诊断已修复，严格全包原有诊断仍未作为通过。

测试使用真实内存撮合与持久所有权组件；200ms 是配置轮询间隔，未作生产时延承诺或固定时长运行验收。完整 Gateway、真实 broker 断连/容器重启及四 Go 服务接入仍需后续验收。运行容器、资金和仓位没有变化，不能将本步测试称为 BTC/ETH 已接管。
