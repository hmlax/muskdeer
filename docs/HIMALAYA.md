# Himalaya 开发做市

此路径只使用现有 `lukla-go` SDK，不改撮合、订单服务、SDK 或目标协议。仅用于已确认的开发测试账户；不代表生产或严格多节点接管验收。

四个核心服务继续各自拥有 Wire、Deer、入口与工作循环：market 提供 Binance USDm 完整二十档；strategy 根据选定来源产生目标订单；execution 持久化意图、预留资金并通过 SDK 执行/撤单；portfolio 从执行服务拉取权威观察并保存可重建 typed 投影。服务间使用 Nacos 发现及 mTLS gRPC，配置仍从 Nacos Proto JSON 读取。

`business.execution_venue=himalaya_sdk` 显式选择此路径，`business.himalaya` 指定账户、产品、二十档/数量比例、杠杆、固定额度及预期 tick/lot。SDK 原生元数据改变时拒绝交易；所选来源失效不切源。当前开发启动选择 Binance USDm，原有 Binance/OKX 现货适配继续保留。行情连接依据 [官方 USDm 连接说明](https://developers.binance.com/en/docs/products/derivatives-trading-usds-futures/websocket-market-streams/Connect)，使用 public 路由。

启动前显式运行 `/himalayainit -enable`：它从 execution 的 Nacos 配置读取已审查的额度，校验核心迁移历史，升级独立 SDK 扩展并初始化/启用本项目预算；不改变原生资金、模式或仓位。服务启动只校验，不自动迁移或启用。SDK token 由 execution 环境变量注入，不写入 Nacos 或源码。Docker 构建使用隔离已验证源码，避免夹带原有未提交修改。

目标数量按外部盘口比例计算，再按原生 tick/lot、最小数量/金额和固定单笔额度约束；同一原生价格合并。最低数量采用稳定的最小合规数量，做市本身不生成测试成交；另见用户新增确认的[开发测试成交策略](SYNTHETIC_TAPE.md)。初次接管只处理已确认的旧 `mm_<SYMBOL>_` 报价；完成接管后若再出现旧生产者报价，拒绝新增风险，不与它争抢。未知来源订单不作为本项目订单擅自撤销。

重报价以二十档目标为准，参考 Himalaya `tools/market-maker/src/reconcile.rs` 的滚动撤补。每侧每轮最多撤补向上取整十分之一的安全待改档位，二十档即两档；其余安全旧单保留完整预留。同价数量尚待更新时仍占据该价位，避免重复补单；缺少的价格优先于数量刷新，买卖新档交替提交。穿越新对侧目标、超过单笔额度及 legacy 的订单继续受控撤除，不适用这项保留额度。

补单同时检查当前原生对侧挂单和本轮已提交报价，禁止交叉，并限制每侧最多比目标多一笔用于交接。前一批撤单没有正向终态时不继续抽走下一批报价，也不续订旧计划的保护期限；行情或计划过期仍受控撤掉全部挂单。存在延后更新的档位时返回 RECOVERING，全部目标完成后才返回 RUNNING，不把维持旧深度当作目标已收敛。

当前没有未决撤单、账户预算和最终授权允许时，缺失方向可先补一笔不会穿越当前原生对侧挂单的新报价，再撤失效旧单。这样在参考价跳出原有窄价带时，先建立能安全接续的一侧；预补与普通下单共用持久化意图、预留、发送窗口及最终 SDK 检查，不跳过未知门禁，也不重复提交已预补的目标。

每笔新单在提交前保存身份、风险预留和行情/策略授权；最终 SDK 发送检查保留的执行、策略、发布租约与期限。配置重试和业务体透明重放关闭。回复丢失进入未知，先查后决定；查不到不视为未成交，也不补发。撤单先记录，回执不释放风险；查询到终态后只释放未成交部分，成交敞口继续保守保留。仓位、旧单、提交中及未知义务都计入风险；额度不随外部盘口自动扩大。

回复丢失且没有原生订单号时，可在同一账户和产品的有界终态历史中按 client_id 找回正向事实；冲突身份或跨账户记录拒绝恢复，未找到仍保留未知和全部预留。活动订单身份在撤单前持久化，避免随后移入历史时失去关联。传输层仅在确定未进入请求体发送时将本次意图作为本地未发送结束；一旦进入 SendMsg，即使返回错误也保留未知，不透明重试。

实盘 SDK 路径在声明发送及最终出口均要求操作、行情授权和资金快照至少还有 500ms 的发送窗口。余量不足时本次不进入 SDK，由后续新计划继续，避免在整组下单接近期限时再发出请求；开发运行的业务操作期限采用 2 秒，所选行情的原有 1.5 秒有效期不延长。该余量不构成上游无超时保证，真正已发送的未知仍保留预留并禁止重放。

SDK 观察由多个查询组成，并非原子账本快照。当前采用保守义务上界及不自动调低的观察值，成交部分不会因相反交易自动净额释放，持续成交可能使预算停止新增风险。该状态需要复核，不通过自动清空预留恢复。

原生接口不接收本项目 epoch，也未确认 client_id 唯一去重或网关失联撤单保证。SDK 出口校验与未知阻断不能撤回目标已接收的请求，进程/网络完全失效时仍有旧挂单风险。不得将本路径描述为撮合级 fencing、STP、原子快照、完整成交账本或生产完成。正常运行的执行保护循环会在来源/计划过期时受控撤单；停止流程同样尝试撤单并保留清理错误。

本轮用户明确批准的旧历史缺失处置见[一次性开发账本基线](DEVELOPMENT_BASELINE.md)；它不重写原撤单证明，也不解除新未知订单的限制。
