# 策略范围的紧急撤单

R08要求紧急撤单展示明确范围、原因及确认；[单笔撤单](ADMIN_CANCELLATIONS.md)不能扩大为全范围成功，Stop和[独立受限平仓](INTERFACES.md)也不是同一动作。P07.58先交付可验证的领域请求和进度推导；本步没有新持久化Model、迁移、RPC、HTTP、页面或执行任务，尚不能通过接口发起范围撤单。

P07.59另增Proto唯一来源的不可变受理结构与schema32；该步骤只有受理结构，未实现仓储或执行任务。执行进度尚未实现，不得把缺少进度行的请求推断为成功。迁移不回填请求，也不主动关闭风险或撤单；受理必须在同一事务写入真实风险关闭及范围审计。新表要求同一策略/操作者/会话/原因、风险修订一增及唯一证据，提交时重新检查会话和当前实际关闭状态。

P07.60接入内部受理/读取仓储：同一授权事务关闭风险、失效旧缓存、写风险关闭及范围审计和不可变受理，任何一步失败全回滚；复用原金融锁顺序。当前operator/admin加独立CSRF才能受理或重放，当前viewer可按策略读取历史。稳定键绑定规范化范围/策略/风险修订/原因，策略互斥后再次读历史，使并发同键得到原记录；不同内容或新键旧修订冲突，后续其他风险修订不重写历史，也不因重放重新关闭风险。

schema33与仓储恢复检查共同拒绝仍未归结的范围，即使暂时没有挂单/动作、市场已经新鲜。P07.60阶段尚无执行进度/完成证明，因此当时所有已受理范围保持待处理；后续以显式持久完成证明接入，不能把空数据或缺行当成功。受理不发执行RPC，不撤销、结算或释放LIVE/INTENT/UNKNOWN义务；完整执行接通前仍无对应HTTP/gRPC路由或页面。

P07.61增加内部有界收录/进度组件和schema34，尚未接到业务进程定期调用或公开管理入口。每次只处理一个范围、至多16个仍有义务的OMS目标，总待处理单笔收据遵守已有256容量；收录前等待所有未归结的新单动作，封存上界后单调推进游标。空页不代表最初无目标，已终态且零预留的历史单可跳过；数据库禁止游标漏掉仍有义务的目标。

范围派生的单笔请求持有可空parent关联，操作者/会话ID、历史角色、原因和策略只能来自原不可变受理与审计。已受理风险减少工作可在原操作者注销后继续，不能借此读取、重放或创建新的管理授权。派生只在持久前缀内成立；普通单笔请求的当前会话/CSRF校验不变，不能把既有请求改接到范围。收录只写元数据，不发送命令；既有StrategyOrderCancellations/StrategyActions及网关承担实际owner/epoch与UNKNOWN恢复。

任务状态来自持久证明，而非读取时根据空计数推断。未收录完、待确认子请求、不明提交、缺失OMS投影的活动核心单或未释放预留都不能成功；已知失败目标仍保留义务。单笔历史失败后若订单后来确已终态且预留归结，范围可按当时权威事实达到终态目标，不改写单笔历史。可以因成交而终止，SUCCEEDED不等于每笔CANCELED或持仓清零。完成标记不能重新打开或改写，管理员恢复还必须通过原有当前资格/资金/市场/配置/目标检查；新风险、别的策略与后来风险修订不属于旧任务结果。

## 词汇与约束

- scope=strategy：只针对明确strategy_id。账户和交易对从该实例读取；不接受隐式account/all范围，不触及共享账户的兄弟策略目标，也不隐式改变desired_state或配置。
- expected_risk_revision：确认该策略独立风险开关的修订，不是实例revision或单个订单revision。后续受理必须在同一授权事务中关闭新增风险、使旧风险授权失效，并记录幂等范围请求及审计。领域Normalize只验证输入，不冒充事务关闭或授权已实现。
- 幂等键：当前operator/admin的16–64 ASCII字符键；策略/明确范围/风险确认/规范化原因绑定同一不可变请求。新请求旧修订冲突，同键异内容冲突，原键重放返回历史收据，不能重新关闭后来已授权恢复的风险。
- 目标收录：必须持久、有界分页，并明确何时全部收录完成；一个空页或零目标计数不等于收录已经完成。不得因单页容量上限截断范围并宣称成功。
- pending_submissions：尚未确认结局的出站新单动作，包括未取得OMS身份的提交/UNKNOWN；不以不存在OMS记录证明未下单。即使当前目标全终态，存在这类动作也必须保持ACCEPTED。
- targets/terminal/failed：同一持久范围内的非负int64计数，terminal与failed互斥。terminal只可来自权威OMS终态及预留已归结的证明，可以是FILLED而不是CANCELED；failed仅表示明确的撤单失败，不释放仍有效的资金/敞口预留。UNKNOWN仍是待办，不能算terminal或failed。

## 进度推导

AdminEmergencyCancelProgress.State先检查计数一致性，用减法检查和的边界，禁止溢出或超额计数。未收录完、仍有pending_submissions、或terminal+failed少于targets时为ACCEPTED；全部归结且有明确失败时为FAILED，全部终态且无失败时为SUCCEEDED。已完成收录的真正空范围可以SUCCEEDED。

这些状态只描述历史工作进度，既不证明风险当前仍关闭，也不授予恢复/下单许可；SUCCEEDED不保证成交未发生或持仓为零。FAILED保留未达到撤单目标的义务，不能因批次结束释放预留。

## 后续持久化与执行验收

下一步用Proto定义唯一持久结构并增加版本化迁移，沿用当前用户/会话复核、既有金融锁顺序和最终执行端fencing。授权关闭和批次必须原子提交，失败整体回滚；受理后不得由HTTP进程直接发送撤单。范围内目标通过现有策略控制器/持久动作/撤单链路处理，所有权替换只能恢复原键，不重造不明动作。

收录/执行未归结时，管理员恢复也须拒绝，不能仅靠临时零挂单窗口重新开风险。并发策略新增/提交与关闭的线性化、分页去重、共享账户隔离、原键重放、注销竞态、旧epoch、部分成交和撤单未知均须用实际数据库/进程行为验证。实现前不得将本领域组件记为紧急撤单功能完成。

领域组件见[P07.58](validation/P07-58.md)，不可变受理结构及schema32见[P07.59](validation/P07-59.md)，原子受理与schema33恢复门禁见[P07.60](validation/P07-60.md)，有界收录/实际取消证明与schema34见[P07.61](validation/P07-61.md)。完整P07/A27和受限平仓仍未完成，无真实资金或生产操作。
