# L1 未受理动作的截止证明

NOT_ACCEPTED只用于本项目当前共享PostgreSQL模拟执行合同。普通NotFound仍是UNKNOWN；只有以下条件共同成立，当前策略owner才可将动作记为NOT_ACCEPTED：

- 持有与execution准入相同的策略行NO KEY UPDATE互斥锁，以及当前策略lease；在READ COMMITTED事务中等待原在途准入结束，使用数据库当前时间。
- 动作Attempt时固定的原deadline已过，且不可修改。提交与取消准入均以数据库时间拒绝过期请求。
- 原账户/业务键没有任何受理记录，检查包含软删除历史；提交还没有原client ID的核心订单或命令，取消没有原稳定核心取消键的命令。
- 提交末尾独立SQL证明上述条件，并永久封住原OMS/取消/核心业务键。延长截止时间或改用直接L1核心调用也不能复活旧动作。

准入在取得策略/执行租约锁之前就取得策略行NO KEY UPDATE；核心触发器重用同一锁，不在持有租约后从SHARE升级。否则另一笔同策略准入可先持有SHARE、等待租约，与核心触发器构成死锁。并发回归在核心写入前暂停，确认第二笔准入真实等待数据库锁，再放行并验证两笔事务及原核心订单均成功。

这不是把缺失结果当作失败：锁使在途准入先结束，原截止时间阻止原包在判定后才被受理，永久记录及数据库门禁阻止旧键续期。已存在受理或效果证据则不能走此路径；真实UNKNOWN继续观察并保留风险预留。回调、查询超时或旧快照都不能提供证明，REPEATABLE READ判定在数据库层拒绝。

SUBMIT的NOT_ACCEPTED没有伪造intent ID或订单状态。CANCEL保留真实目标intent ID，但没有伪造取消回包，也不解冻父订单或释放其预算。动作离开活动集合后，控制器只能从当前状态/配置/行情生成新的决策；原动作Attempt/业务键永久不可复用。已受理的相关OMS和取消历史禁止删除、软删除或改写业务身份，避免把证据消失当成未受理。

核心取消键保持既有`cancel:`加SHA-256(account + 换行 + 原RPC键)，没有改历史公式。SQL证明使用PostgreSQL内置[二进制哈希及编码函数](https://www.postgresql.org/docs/16/functions-binarystring.html)，不新增扩展或小数转换。

该证明依赖本L1数据库准入/最终核心门禁，不直接推广到外部交易所。P11真实适配器需独立确认同等请求截止、持久幂等、在途序列化和权威效果查询合同；不能用本地动作状态冒充真实交易所的否定回执。
